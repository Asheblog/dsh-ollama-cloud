# ADR 0005 — 配置的端点就是目录，内置快照只是兜底

状态：已接受（2026-10-03）

## 背景

`0.1.0` 发布时带的是一份人工整理的目录：2026-09-29 当天 Ollama Cloud 提供的
17 个模型，以及那天 `POST /api/show` 报出的上下文窗口、输入类型与思考档位元数据。
插件对外提供的每一项能力——包括 composer 里 Effort 选择器的可选档位、会话没选时
materialize 的默认档位——因此都是某一次端点回答的副本，在发布那一刻被冻结。

Ollama 并不会冻结：它会新增模型、下架模型（`410`，且 id 有时仍在清单里挂一阵），
也会在版本之间改动某个模型的 `thinking` 元数据（档位集合与默认值）。由此产生两个
后果，而且都真实发生过：

- **已下架的模型继续被提供。** route 宣称的就是自己目录里的内容，于是选择器会提供
  一个在请求时返回 `410` 的模型，而用户看到的是一个供应商错误，而不是"这个模型没了"。
- **新增模型与改了档位的模型都要等一次插件发布。** `0.2.x` 通过 `llm/discoverModels`
  拿到了实时清单，但那条通道是**咨询性**的：宿主把答案交给配置页决定是否采纳，自己
  什么都不存；而且 harness 自己的 `LlmDiscoveredModel` 形状里根本没有推理元数据。
  没有任何东西会刷新 route，所以现实中的做法就是带着新快照再发一版插件——这恰恰是
  插件本身要消除的维护负担（`0.2.x` 开发期间就为了 `deepseek-v4.1-flash` 发生过一次）。

目录还必须撑过两种刷新不能假定其不存在的情况：启动时端点不可达，以及端点能回答
`/api/tags` 但某次 `/api/show` 失败。

## 决定

1. **一次刷新读取端点并采纳答案，在装载时与按间隔各执行。** 由 `live-catalog.ts`
   完成：`GET <base>/tags` 决定成员，逐个模型 `POST <base>/show` 取元数据，解码复用
   咨询性发现面用的同一个 `decodeShowResponse`，因此"用户可采纳的能力"与"route 提供
   的能力"永远不会互相矛盾。装载时这一趟**不阻塞启动**（端点慢不能拖住 boot），并发
   受控所以两趟不会重叠，失败只记日志并保留正在使用的目录。`autoRefresh`（默认
   `true`）与 `refreshMinutes`（默认 `1440`）控制它，且定时器每趟都重新读取实时配置。
2. **目录是分层的，每层只回答它知道的事。**

   | 层 | 权威范围 |
   | --- | --- |
   | `models:` 配置 | 按 id 覆写，以及 `enabled: false` 下架 |
   | 刚抓取的端点答案 | 成员资格，以及每个模型声明的能力 |
   | 上次抓取的缓存 | 同一份答案，先于网络响应读出 |
   | 内置快照 | 显示名，以及首次抓取前的兜底 |

   合并策略在 `catalog.ts`（`mergeCatalogEntry`）：端点回答过的字段一律以端点为准，
   它没回答的由快照补，并且 **"端点什么都没说"**（省略 `reasoningEfforts`）与
   **"端点说了不能思考"**（`reasoningEfforts: false`）严格区分。默认档位只在档位集合
   没被改动时才继承——与配置层早已遵循的规则一致。
3. **成员只会因"下架"而减少，不会因"沉默"而减少。** `discoverCatalog` 把三种结果分开，
   因为它们含义不同：*described*（有元数据）、*retired*（`404`/`410`——端点自己说它的
   清单过期了，从目录中剔除）、*unknown*（超时、5xx、429——模型保留，只带清单给出的
   信息）。没有最后一种，一次慢 `/api/show` 就会让真实模型消失整个刷新间隔；没有
   retired 这一种，选择器就会提供一个无法应答的模型。**空清单**直接拒绝本次刷新：
   一个空荡荡的模型选择器是 UI 无法自愈的状态，而"所有模型同时下架"比"网关抽风"的
   可能性低得多。
4. **缓存让重启——以及离线启动——变得诚实。** 它放在 harness home 下
   （`<DSH home>/cache/dsh-ollama-cloud/catalog.json`），而不是安装包里，所以重装或
   更新插件不会丢；写入是原子的（临时文件 + rename），读取时整体校验（某一条不合法
   就丢弃整个文件，而不是提供一个只可信一部分的目录）。一次只保存一个端点：来自
   另一个 `baseURL` 的缓存会被忽略，而不是被合并。
5. **采纳结果通过 revision 到达运行中的会话，而不是靠重载。** `CatalogSource.revision()`
   加入连接读取器 memoize 的 volatile 引用集合（`createConnectionReader`），因此采纳
   一个变化的目录会重新解析 route、用请求路径读到的同一份事实重建适配器 profile，
   模型清单、上下文窗口与档位档位一起更新。只是**确认**了目录的那一趟不会推进
   revision，所以不会白白重建。

已否决：**让快照保持权威、每次变更发一版**——这正是本 ADR 要消除的维护负担，而且它
无法应对两次发布之间的下架。已否决：**自动调用 harness 的 `llm/discoverModels` 并把
答案写进用户设置**——那条通道是给配置页里的**草稿**端点用的，不带任何推理元数据，而
用后台定时器去写用户配置会让插件自己的目录对刚写入的设置层不可见。已否决：**不做缓存
的刷新**——那样每次启动的第一份模型清单都要和网络赛跑，离线启动则只能提供一份没人知道
年龄的快照，而这恰恰是要修掉的失效模式。已否决：**用 TTL 跳过装载时刷新**——请求只是
一次匿名清单加每个模型一次，而"以本次启动为准"就是全部承诺。

## 后果

- Ollama 新增、下架或改了档位的模型，会在下一趟（最多一个间隔）到达运行中的会话，并在
  之后每次启动时于装载阶段到达，不需要任何插件发布。仓库里的快照仍在，作为离线层与
  显示名来源；它不再是正确性面，因此快照过期只是观感问题，不再是路由问题。
- 新增两个配置字段，都按实时值读取。设 `autoRefresh: false` 就精确复现 `0.3.0` 之前的
  行为（先缓存、再快照），这也是气隙环境或受限额度部署下最诚实的说法。
- 缓存按 harness home 与端点隔离；切换 `baseURL` 的用户在新端点回答前走快照。这是有意
  的：跨端点合并目录会提供配置端点根本没有的模型。
- `discoverCatalog` 现在区分"下架"与"失败"，咨询性的 `llm/discoverModels` 面因此继承
  同一条规则：`404`/`410` 条目不再是候选，未被描述的条目同样不是（采纳需要元数据）。
- 测试套件改用一次性的 `DSH_HOME`：缓存让插件的测试有能力写进开发者真实的目录，而
  一个采纳了假目录的测试否则会决定下一次真实启动提供什么。
